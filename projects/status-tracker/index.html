Status Tracker

A team check-in app where the hard part is not the check-in. Every status change posts to a Google Chat webhook — and almost all of the engineering went into deciding when not to send one.

What it is

Team members post a daily status — In Office, Work From Home or On Leave. The app records it in Firestore, shows the team a live feed, and pushes a formatted message to the team's Google Chat space. Managers get a console to override statuses and configure the webhook.

Overview

Most small teams track "who is in today" in a chat thread that nobody reads back. Status Tracker turns that into structured data: one document per person per day, a live team view, personal history — and, crucially, the same Google Chat message everyone was already getting, posted automatically.

It is the largest thing I have built alone: 107 commits, 4,833 lines across the app, server routes and configuration, developed on feature branches and merged through pull requests.

Problem

A notification integration is trivial to build and easy to make unbearable. The first working version posted to Google Chat on every click. Change your mind twice and the team channel has three messages about you. Double-click the button and it has two identical ones.

There is also a subtler failure. If the app writes the status to the database first and the webhook then fails, the record says the team was told something it was never told — and the deduplication logic, which reads that record, will now refuse to send the message that never arrived.

So the real requirement was not "send a notification". It was: send exactly one message per genuine change, never claim to have sent one that failed, and make all of that survive a page refresh.

Solution

  • Notifications move through a Nitro server route rather than the browser, so the guard logic and the Admin credential live somewhere the client cannot edit.
  • Three separate suppression rules: the same status already broadcast today is a silent no-op, a genuine change within 60 seconds returns HTTP 429 with the remaining time, and a second change later in the day asks for confirmation first.
  • The webhook is awaited before the Firestore write, so a failed or rate-limited send leaves no record behind.
  • Two separate fields — status (what the user picked) and notifiedStatus (what the team was actually told) — because a manager override changes one without changing the other.
  • The cooldown is reconstructed from Firestore on load, so closing the tab does not reset it.

Technical implementation

  • SPA with a server tail. ssr: false makes this a single-page app, but it still needs a Node host: the two Nitro routes hold the Admin credential and the webhook logic. A purely static deploy would break notifications.
  • Deterministic document IDs. Status documents are keyed {uid}_{YYYY-MM-DD}, so "one check-in per person per day" is enforced by the key rather than by a query. The date comes from toLocaleDateString('en-CA'), which yields an ISO-shaped local date.
  • Blocking auth bootstrap. The client plugin returns a Promise that resolves inside onAuthStateChanged, so route middleware never runs against a half-loaded session. It also creates the Firestore profile on first sign-in.
  • Two-stage route gating. auth.js handles session and team membership — a signed-in user without a team is pushed to onboarding. manager.js is a separate role gate applied only to the team console.
  • Singleton composables. useUser and useTheme declare their refs at module scope, so every component shares one instance without a store library.
  • Theme applied before hydration. An inline script in the document head reads localStorage and sets the class before Vue mounts, so dark-mode users never see a white flash.

Key decisions

Send the webhook before writing to the database

The natural order is to save then notify. I inverted it. The webhook call is awaited first, and only on success does the status document get its notifiedStatus and lastNotifiedAt. If the send throws — bad URL, network failure, cooldown — nothing persists, so the record can never claim a message the team never received. The comment explaining this is in the source, because it is exactly the kind of ordering a later change would quietly undo.

app/components/status.vue — doNotify(); server/api/notify.post.js

Guard on the server, mirror it on the client

The duplicate check and the 60-second cooldown both live in the server route, which is the only place they can actually be enforced. The client repeats them — a toast for a duplicate, a disabled button with a live mm:ss countdown during cooldown — purely so the user finds out before making a request. The server returns retryAfterMs with its 429 so the two stay in sync.

server/api/notify.post.js COOLDOWN_MS; status.vue notified()

Separate "what you picked" from "what was announced"

A manager overriding someone's status broadcasts a different message and must not corrupt that person's own cooldown state. Splitting status from notifiedStatus lets the two legitimately diverge, and every write uses { merge: true } so no path can blank the other's fields. Duplicate detection reads notifiedStatus and falls back to status for documents written before the field existed.

status.vue, team.vue — setDoc(..., { merge: true })

Rebuild the cooldown from the database, not from memory

A timer held in component state resets the moment the tab reloads, which makes a client-side cooldown decorative. On load the app reads lastNotifiedAt from today's status document and restarts the countdown with whatever time is left.

status.vue — loadTodayStatus() → startCooldown(remaining)

Store the webhook per team, not in the environment

The Google Chat URL lives in teams/{id}.webhookUrl and is set by the manager in the UI. Each team points at its own space and a redeploy is not needed to change it — at the cost of an unvalidated URL in the database, noted below.

team.vue saveWebhook(); notify.post.js reads teamSnap.data()

Initialise the Admin SDK lazily

Building the credential at module load meant a malformed service-account key crashed the entire Nitro bundle at boot, before any request could be served — including the pages that do not need Firestore. Moving it behind a getAdminDb() accessor turns that into a single failed API call. The helper accepts base64 or raw JSON because multi-line keys in .env break differently on Windows.

server/utils/firebaseAdmin.js

Challenges

Deciding what counts as a duplicate

"Already notified today" is not one condition. Re-sending the same status is noise and should be silently dropped. Changing status genuinely matters and should go through — but the second, third and fourth change in a day are increasingly likely to be fidgeting. The resolution was three different responses: silent no-op, confirmation modal, and a hard rate limit, rather than one blanket rule.

Modals drifting off-screen on mobile

Confirmation dialogs rendered inside their parent component were positioned relative to a scrolled, transformed ancestor and ended up below the fold on phones. Moving them into <Teleport to="body"> with a fixed 100dvh overlay fixed it for every case at once.

Android Chrome overriding the dark theme

Force Dark applied its own inversion on top of the app's palette a moment after load, producing a flash of correct styling followed by flat black. Declaring color-scheme in both the meta tag and on the document element told the browser the page handles this itself.

Timestamps arriving in two shapes

Status documents can hold timestamp as a raw number or as a Firestore Timestamp depending on which code path wrote them. Date filtering had to normalise both, or members silently showed as "No check-in".

Trade-offs

Client SDK for reads, server route for notifications

Reads and status writes go straight from the browser to Firestore, which is what makes the live feeds simple and cheap. Only the webhook path is server-side. That split is why Firestore rules matter so much here — and why leaving them open is the most serious gap in the project.

SPA mode instead of SSR

Every page is behind authentication, so server rendering buys nothing for SEO and would complicate the Firebase auth bootstrap. The cost is a blank first paint until the bundle loads.

Client-side date filtering

Live queries fetch the team's status documents and filter to today in the browser. That avoids composite indexes and keeps one subscription serving several views, but it transfers more documents as history grows. Fine at team scale; wrong at organisation scale.

Google Chat only

The message payload is built for Chat's incoming-webhook format. Slack or Teams would need an adapter layer that does not exist yet.

Security

  • Authentication is Firebase Auth — email/password and Google popup. Passwords are never handled by application code.
  • The service-account credential is read only from FIREBASE_SERVICE_ACCOUNT_KEY and has never been committed — no .env or key file appears anywhere in the 107-commit history.
  • The Firebase web config in the repository is the public client identifier, which is public by design for web SDKs. It is not a secret; Firestore rules are the real boundary, which is precisely why the gap below matters.
  • Route middleware enforces session, team membership and manager role on the client, and the manager-only console is a separate gate rather than a hidden link.
  • Specific Firebase error codes are surfaced as human messages rather than raw exceptions.

Limitations

What is wrong with this project

Ranked by what I would fix first. All four were confirmed by reading the source, and the project's own README flags the first one too.

1 · Firestore rules are wide open

firestore.rules is still the Firebase starter template — allow read, write: if true, comment and all. Because the client SDK talks to Firestore directly, anyone with the project ID can read or write every collection regardless of what the UI allows. The route middleware is a navigation convenience, not a security boundary. This is the single most serious issue in the project and the first thing I would fix: per-collection rules keyed on request.auth.uid and team membership.

firestore.rules — unchanged default

2 · The API routes verify no identity token

/api/notify and /api/update trust the uid and teamId in the request body. There is no verifyIdToken call anywhere in the server directory, so a crafted POST could post a message as another member. The fix is to send the Firebase ID token in an Authorization header and verify it with the Admin SDK before doing anything else.

no Authorization or verifyIdToken usage under server/

3 · The webhook URL is never validated

Whatever a manager pastes into the webhook field is stored and later POSTed to by the server. Nothing checks that it is a URL, let alone a chat.googleapis.com one — which makes it a server-side request forgery vector. It needs URL parsing and a host allow-list at write time and send time.

notify.post.js / update.post.js — webhookUrl passed straight to $fetch

4 · The cooldown is read-then-write, not transactional

The route reads lastNotifiedAt, decides, then writes. Two requests arriving in the same instant can both read a stale value and both send. A Firestore transaction would close the window. In practice it needs simultaneous clicks to trigger, but it is a real race and not a hypothetical one.

no runTransaction in the codebase

5 · No automated tests, and some dead code

Everything was verified by hand; the notify guard is pure decision logic and the obvious first thing to unit-test. functions/index.js is also a leftover Cloud Function writing to an unused users collection — superseded by the Nitro routes and safe to delete.

no test files; no CI workflow; functions/index.js unreferenced

6 · Join codes can collide

Team join codes are six random digits with no uniqueness check. At a handful of teams the odds are negligible; the lookup would still return the wrong team if it ever happened.

welcome/create.vue — Math.floor(100000 + Math.random() * 900000)

Testing & deployment

  • Verified by hand across sign-up, Google sign-in, team creation, joining by code, status check-in, duplicate suppression, the cooldown countdown and its restoration after a refresh, manager override, member removal and dark mode.
  • No automated test suite and no CI pipeline — stated plainly above rather than implied.
  • Deployed on Vercel from master. The most recent production deployment reports success on the current HEAD commit, and the repository is still connected after the account transfer — a preview build was produced for the latest push.
  • Live at team-status-tracker.vercel.app, checked 17 September 2026: the root path redirects to /login, which confirms the auth gate is active in production. A second Vercel alias serves the same project.
  • Firestore is pinned to the asia-south2 region; rules and indexes deploy separately through the Firebase CLI.

Lessons

  1. The order of two awaits can be a correctness decision. Notifying before persisting is the difference between a record that might lie and one that cannot.
  2. A client-side rate limit is a UI affordance, not a rate limit. If it is not enforced where the user cannot reach it, and not rebuilt from storage on load, it does nothing.
  3. "Already done today" was three different conditions wearing one name. Splitting them produced three different, appropriate responses.
  4. Convenient defaults are the ones that ship to production. Open Firestore rules were a reasonable way to start and an unreasonable thing to still have — writing this case study is what made me rank it as issue number one.
  5. Moving initialisation from import time to first use turned a total outage into a single failed request.

What I would do next

  • Write real Firestore security rules keyed on request.auth.uid and team membership.
  • Verify the Firebase ID token on both API routes before trusting any body field.
  • Parse and host-allow-list the webhook URL at write time and send time.
  • Make the cooldown check a Firestore transaction.
  • Unit-test the notify guard — duplicate, cooldown and confirmation paths.
  • Add team-wide reports for managers; today reports are personal only.
  • Delete the legacy Cloud Function.
